# session-phases.md（タスクᴳ進行と開発フェーズᴳ定義）

- 対象: `~\Projects` 配下で行う全タスクᴳ
- 位置づけ: CR-048 / CR-049 / CR-050 / CR-054 / CR-056 / CR-057 / CR-058 / CR-065 / CR-093 / CR-094 が参照する規範手順。セッション遷移手続きᴳ、再開記録、タスクᴳ種別、適用経路、開発フェーズᴳ、成果物、DoDᴳの正ᴳとする
- 使い方: 全タスクᴳでフェーズᴳ 0を行い、適用表で以降の経路を決める。実装・挙動変更を伴う開発はフェーズᴳ 2〜7を省略せず、前フェーズᴳの成果物が未合意のまま次へ進まない
- 確認規則: フェーズᴳ成果物は依頼者または依頼者指定の承認者との合意後に確定する。操作単位の確認は CR-019 / CR-051 / CR-073 に従う

## セッション遷移手続きᴳの関係

開始・再開・引継・終了の各手続きは、番号付きの開発フェーズᴳではなく、セッションとタスクᴳの状態を安全に遷移させるための手続きとする。

1. 全セッションで開始手続きᴳを行う
2. 継続中タスクᴳ、再開用プロンプト、または過去タスクᴳの続行指示がある場合は再開手続きᴳを行う
3. タスクᴳ途中で会話文脈・担当・ツールを意図的に切り替える場合は引継手続きᴳを行う
4. タスクᴳが完了した場合だけ終了手続きᴳを行う

## 開始手続きᴳ（固定・合意不要）

セッション開始時に毎回固定で実行する。

1. 使用中AIツールに対応する入口ファイル → `CROSS_PROJECT_RULES.md` の順で読む
2. 特定プロジェクトが対象の場合だけ `PROJECT_RULES.md` → `resume.md`（あれば）を読む
3. 継続中タスクᴳ、再開用プロンプト、または過去タスクᴳの続行指示を検出した場合は、フェーズᴳ作業へ入る前に本書の再開手続きᴳを行う
4. `04_Rules_Reference\README.md` の参照トリガーに該当する文書を読む

## 再開手続きᴳ

開始手続きᴳ後、継続中タスクᴳ、再開用プロンプト、または過去タスクᴳの続行指示がある場合に実行する。再開用プロンプトが利用できる通常再開と、欠落・不完全・陳腐化している場合の復旧再開に分ける。

### A. 通常再開

1. 再開用プロンプトに指定された `resume.md`、最新の節目 handoverᴳ、現在タスクᴳのtask-recordsᴳ・仕様・設計を順に読む。`worklog.md` は差異・ブロッカー・詳細経緯の確認が必要な場合だけ末尾を読む
2. プロジェクトルートとnested repositoryを区別し、Gitリポジトリでは実行ユーザー、branch、HEAD、upstream、ローカルremote-tracking ref、ahead／behind、tracked、staged、unstaged、untracked、引継ぎ記載の変更ファイルをread-onlyで照合する。remote refを更新する `fetch` は自動実行しない
3. 現在タスクᴳとゴール、現在フェーズᴳと状態、直近完了ステップᴳ、次のフェーズゲート、未解決・ブロッカー、検証待ちキューᴳ、AI側と依頼者側の残作業を特定する
4. 引継ぎ記載と実状態の差異、未確認事項、次に扱うexact filesと方針を報告する
5. 引継ぎまたはフェーズᴳ定義がread-only停止を指定する場合、実状態に重大な差異がある場合、または新しい合意・承認が必要な場合は変更せずに停止する。それ以外は、承認済みフェーズᴳ範囲内の可逆な作業を再確認せず継続できる（CR-051）

### B. 復旧再開（再開用プロンプトを利用できない場合）

1. `resume.md` → `resume.md` が参照する節目 handoverᴳ → `worklog.md` 末尾 → 現在タスクᴳと思われるtask-recordsᴳ・仕様・設計の順に読む。handoverᴳ参照がない、壊れている、または曖昧な場合は、`handover-YYYY-MM-DD[-N].md` のファイル名上の最新候補を確認し、候補が複数なら必要な候補をすべて照合する
2. Gitリポジトリでは `status`、branch、HEAD、upstream、ローカルremote-tracking ref、ahead／behind、unstaged diff、staged diff、untracked一覧を取得し、変更済み・新規ファイルの内容をread-onlyで確認する。Git外のプロジェクトでは、引継ぎ資料が指す成果物と現在ファイルを照合する
3. 現在タスクᴳ、現在フェーズᴳ、完了済みと考えられる作業、途中状態、未検証事項、ブロッカー、次の一手を復元し、各項目を `確認済み`（直接確認できる）/ `推定`（複数の痕跡から推定できる）/ `不明`（確認根拠がない）に分ける
4. 状態復元では、依頼者の現在指示から作業範囲と承認境界、入口・共通・プロジェクト規則から制約、Git・ファイルシステムから現在の事実、`resume.md`・最新handoverᴳ・`worklog.md`から記録済み経緯を確認する。過去会話と推定は補助根拠に限る
5. ファイルの存在・差分だけを、テスト成功、フェーズᴳ完了、依頼者承認、Git状態変更、外部環境操作、production状態の根拠にしない。確認できないものは `不明` または検証待ちキューᴳとする
6. 初回復元中はファイル編集・生成・format・test、Git状態やrefの変更、remote `fetch`、temp／cache削除、外部環境操作を行わない
7. 復元結果、差異、確度、未確認事項、次に扱うexact filesと方針を報告し、原則として続行合意を待つ。ただし、依頼者の現在指示が照合後の続行まで明示し、タスクᴳ・フェーズᴳ・変更範囲が一意で、重大な差異・未通過ゲート・ブロッカー・権限不足がない場合は、承認済み範囲を継続できる
8. 続行合意後、必要なら `resume.md` と引継ぎ資料の不整合を修復してからフェーズᴳ作業へ戻る

### 再開手続きᴳの完了条件

- 読み順とread-only照合を完了し、現在タスクᴳ、現在フェーズᴳ、次のゲート、ブロッカー、未検証事項、次の一手を特定している
- 引継ぎ記載と実状態の差異、確度、続行に必要な合意・承認の有無を報告している
- 必要な停止ゲートがある場合は、変更を開始せず依頼者の合意・承認を待っている

## チェックポイントと再開記録（CR-054 / CR-056）

プロジェクト作業の継続記録に適用する。CR-068対象の横断作業は継続記録を作らず、最終報告を用いる。

### 更新契機と鮮度（CR-054）

- 工程完了・重要判断・長時間または不可逆な操作の前後・中断・担当やツールの切替をチェックポイントᴳとし、`worklog.md`へ差分を追記して`resume.md`を最新化する。同じ説明を複数文書へ重複転記しない
- 各フェーズᴳは完了時に`worklog.md`へ1エントリを記録し、複数フェーズᴳを1エントリにまとめない
- フェーズᴳ着手時に`resume.md`の現在地点を「着手」へ更新する。長い工程は主要な節目で「進行中の途中状態」を更新し、自律実行・長時間実行でも省略しない
- 非意図的な中断後に再開用プロンプトがなくても復旧再開できるよう、`resume.md`を常に1フェーズᴳ以内の鮮度に保つ

### resume.mdの必須項目（CR-056）

次セッションが即再開できる最小量で、次の項目を記録する。記入様式は`00_Template\handover\resume.md`を用いる。

- 更新時刻、実行ツール・セッション、workspace rootとnested repository
- Gitモード、worktree path、base／作業branch、HEAD、remote、commit・remote branch・PR
- 現在タスクᴳとゴール、現在フェーズᴳと状態、直近完了ステップᴳ、次の一手、途中状態
- 未解決・ブロッカー、検証待ちキューᴳ、続行に必要な合意・承認
- 最新handoverᴳと関連文書

CR-054の着手・途中・完了の更新と鮮度の条件は、2026-08-29改訂の本文から集約した。

## 引継手続きᴳ

次の営業日以降への持ち越し、担当・AIツールの交代、現在の会話文脈だけでは安全に再開できないセッション分割など、タスクᴳ途中で文脈を意図的に切り替える場合に実行する。短い同一文脈の中断では実行せず、CR-054 のチェックポイント更新だけを行う。トークン上限・強制終了・障害などの非意図的な中断で本手続きが実行できなかった場合は、次セッションで復旧再開を行う。

1. `worklog.md` へ、直近チェックポイント以降の実施内容、変更ファイル、決定と理由、検証結果、次の一手を追記する。既存エントリは書き換えない
2. `resume.md` を、現在タスクᴳ・現在フェーズᴳ・途中状態・作業ツリー・未解決・検証待ちキューᴳ・次の一手を示す最小限の正ᴳとして更新する
3. CR-058 に従って新しい `handover-YYYY-MM-DD[-N].md` を作成し、当該区間のworklogᴳを要約する。過去handoverᴳは原則として書き換えない
4. 節目 handoverᴳ末尾に `## 再開用プロンプト` を設け、コピーして次のAIセッションへ入力できる自己完結したプロンプトを作成する。同じプロンプトを依頼者への最終回答にも提示する
5. `resume.md`、`worklog.md`、節目 handoverᴳ、task-recordsᴳ間で、タスクᴳ、フェーズᴳ、Git・ファイル状態、次の一手、ブロッカー、検証結果が矛盾していないことを確認する

### 再開用プロンプトの必須項目

- 対象プロジェクト、workspace root、nested repository、使用するAI向け入口ファイル
- 入口 → `CROSS_PROJECT_RULES.md` → `PROJECT_RULES.md` → `resume.md` → 指定handoverᴳ → 指定task-recordsᴳ・仕様・設計 → 必要時の `worklog.md` 末尾、のexact paths付き読み順
- 現在タスクᴳとゴール、現在フェーズᴳと状態、直近完了ステップᴳ、次のフェーズゲート
- branch、HEAD、upstream、ローカルremote-tracking ref、ahead／behind、tracked、staged、unstaged、untracked、保護すべき既存変更
- Git実行モード、worktree path、base／作業branch、remote／PR base、実行主体、最新commit、remote branch、PR URL
- 完了事項、途中状態、最後に成功・失敗した検証、検証待ちキューᴳ、未確認事項
- 未解決、ブロッカー、AI側と依頼者側の残作業、次に扱うexact filesと方針
- 禁止操作、追加承認が必要な操作、再開初回のread-only停止と続行合意の要否

### 引継手続きᴳの完了条件

- `worklog.md`、`resume.md`、新しい節目 handoverᴳが役割分担され、相互に矛盾していない
- 節目 handoverᴳ末尾と依頼者への最終回答に同じ再開用プロンプトがあり、読み順・現在地点・差分・検証・権限境界・次の一手が自己完結している

## 終了手続きᴳ（タスクᴳ完了時）

タスクᴳ完了時だけ実行する。フェーズᴳ 8〜10 と必要な反映後確認の結果を照合する手続きであり、対象リポジトリ内のファイル編集・生成・移動・削除を行わない。文書整備、完了配置への移動、参照修正、削除を伴う後始末はフェーズᴳ 9までに済ませる。タスクᴳ途中の意図的な中断には引継手続きᴳ、非意図的な中断後には復旧再開を適用する。

1. 完了基準を確認する: 選択したGit実行モードのPhase 10完了条件を満たし、PRを使う場合は人間mergeと必須CIの成功を確認する。今回の完了条件に含まれる配備・実機確認も済み、必須検証の残件がないことを確認する（CR-066）。PR引渡し済み・CI実行中・必須確認待ちはタスクᴳ完了としない。明示裁定で後続へ分離した事項は未実施のまま記録し、成功扱いにしない。
2. 成果物の確定を確認する: task-recordsᴳ の `draft` 除去済み・`task-records/completed/`（完了済み層）へ移動済み、現行の正ᴳ（`specs`/`design`/`adr` 等）へ反映済み（フェーズᴳ 8 の取りこぼし点検）
3. 対象リポジトリ外の引継ぎ資料を整備する: 節目 handoverᴳ を作成（CR-058）、`resume.md` を「進行中タスクᴳなし」の短い再開地点へ整理（CR-056/059）、`worklog.md` へmerge SHA・CI・反映後確認を含む完了エントリを追記する（CR-054）。記録先が対象リポジトリ内にある運用では、フェーズᴳ 0で合意した外部記録先を使う。CR-068対象は最終報告へ記録する。
4. 対象リポジトリ外の完了履歴を更新する: プロジェクト規則がある場合、ロードマップ等の該当タスクᴳを完了履歴へ移す（例: `temp/ROADMAP.md` → `handover/completed-tasks.md`。PJ-015）。対象リポジトリ内の資料は反映前に確定した成果物として保持し、merge済み等の追記だけの追加PRを作らない。
5. 振り返りをクローズする: フェーズᴳ 9 のルール追記候補が裁定済み、失敗記録台帳へ記録済み、CR-008 の全体棚卸しトリガー該当の有無を確認する
6. 後始末の実施結果をread-onlyで確認する: 一時資料の裁定・参照修正が済み、意図しない差分がないことを照合する。既存の混在差分・temp/cache・branch/worktreeの保護と削除権限を維持する。変更漏れや不具合が見つかった場合は終了手続きを止め、該当工程へ戻って修正・再検証する。終了手続きの名目で修正を隠さない。
7. 依頼者側に残る作業（デプロイ・別リポジトリのコミット・棚卸し等）を `resume.md`／handoverᴳ へ「残」として明示する

## フェーズᴳとステップᴳの判定基準

- フェーズᴳに切り出す条件（4つすべて）: ①独立した引継ぎ可能な成果物を生む ②固有の完了条件を持つ ③成果物が次フェーズᴳの入力になる ④単独でスキップまたはセッション分割の境界になり得る
- ステップᴳ: 上記を満たさず、フェーズᴳの単一成果物へ収束する内部手順
- 各フェーズᴳは インプット / ステップᴳ / アウトプット / 完了条件 の4項目で記述する

## タスクᴳ種別ごとの適用経路・成果物・DoDᴳ

- フェーズᴳ 0で主種別を1つ、副種別を0個以上選ぶ。主種別の経路を基準に各種別の適用工程を和集合し、番号付きフェーズᴳは昇順で進め、成果物とDoDᴳを合算する
- 実装・挙動変更が主種別または副種別に含まれる場合は、フェーズᴳ 2〜7を省略しない
- 調査が後工程の前提になる場合はフェーズᴳ 0直後、レビューが後工程の成果物を対象にする場合は対象成果物の作成後かつフェーズᴳ 8の前に実施する。複合時の実行順をタスクᴳ定義へ記録する
- 仕様書・設計資料では、新規または変更する最上流から必要なフェーズᴳ 2〜4を適用する。承認済み上位成果物を再利用する場合だけ前段を省略でき、参照先・版／基準時点・今回も有効と判断した根拠をタスクᴳ定義へ記録する
- 非該当フェーズᴳと理由、採用した経路、DoDᴳはタスクᴳ定義へ記録する
- フェーズᴳ 9（振り返り）は全タスクᴳ種別で適用する。フェーズᴳ 10（コミット）はリポジトリ内の変更がある場合のみ適用する

### 開発の標準順序（CR-049）

開始手続きᴳ → 継続中なら再開手続きᴳ → タスクᴳ定義 → Gitモードに応じた記録初期化・branch／worktree準備 → 要件定義 → 基本設計 → 詳細設計 → テスト実装 → 実装 → リファクタ → 文書整備 → 振り返り・変更漏れ確認 → exact stage・commit・push・PR引渡し → 人間merge・必須CI・必要な反映後確認 → 終了手続きᴳの順で進める。

`human`・非Git作業には適用表とフェーズᴳ 10の実行主体・非該当条件を適用し、先行反映・修正には次節の専用経路を用いる。リポジトリ内変更を原則PR前に集約し、終了手続きᴳでは対象リポジトリを編集せず外部の完了記録だけを更新する条件は、2026-09-09のCR-049改訂と同じである。

### 反映後のremote証跡を要する経路

- 適用条件: 必須証跡をcommit・配備後のCIまたはremote環境でしか取得できない場合。安全性・復旧手順・検証手順と権限は反映前に確定する。release以外の検証環境への先行反映が必要な場合も、理由と実行順を事前に合意する。
- 原則経路: `0 → … → 7 → 8（反映前成果物確定）→ 9 → 10 → 人間merge・必要な配備／検証 → 終了手続き`。配備の実行順は合意済み環境・権限に従い、Git委譲だけで配備を許可しない。
- フェーズᴳ 8で対象TC-IDᴳを `反映後確認待ち` として保存し、検証方法・期待結果・対象版を識別する方法・対象リポジトリ外の証跡保存先を確定する。この経路に限り、反映前に可能な検証がすべて合格なら成果物を確定できるが、タスクᴳ完了・未実施TC-IDᴳの合格を宣言しない。
- 反映後は外部記録先へ `TC-IDᴳ / 対応AC-IDᴳまたは直接検証 / 最終状態 / 対象commit・環境・証跡` を保存する。リポジトリ内の反映前スナップショットと外部の最終結果を合わせて受入記録とし、結果転記だけの完了記録コミットを要求しない。
- 検証失敗や仕様・実装の変更が必要なら該当工程へ戻り、修正・再検証を行う。merge前は同一PRへ追加pushし、merge後は修正scopeとGit権限を確認する。回数削減を理由に検証や人間reviewを省略しない。

### 調査／レビュー実施単位

- インプット: 合意済みタスクᴳ定義 / 複合タスクᴳでは対象となる前段成果物
- ステップᴳ: 対象範囲を固定する → 一次根拠を収集する → 根拠と推論を分けて分析する → 結論・重大度・対応要否・未確認範囲を整理する
- アウトプット: 根拠付き調査結果または指摘一覧。変更を伴う複合タスクᴳでは後続フェーズᴳの入力、読取専用では完了報告とする
- 完了条件: タスクᴳの全TC-IDᴳを直接証跡または指摘結果へ対応付け、依頼者が成果物に合意する

### 非開発成果物の作成・変更実施単位

- 対象: フェーズᴳ 2〜7を適用しないドキュメント・ルール変更。仕様書・設計資料は適用するフェーズᴳ 2〜4で作成する
- インプット: 合意済みタスクᴳ定義 / 必要な調査結果 / 既存の正ᴳ
- ステップᴳ: 正ᴳと依存する参照先を確認する → 合意済み範囲の成果物を作成・変更する → 索引・入口・検査等の依存箇所を同期する → 差分を目視する
- アウトプット: 更新した文書・ルールと、各TC-IDᴳに対応する検証方法・証跡
- 完了条件: 合意済みスコープの成果物が作成され、全TC-IDᴳの検証先が定まり、依頼者が成果物に合意する

## 成果物の配置（docs/task-records）

リポジトリ内の開発タスクᴳでは、フェーズᴳ 0〜5 のmd成果物をタスクᴳ単位ディレクトリへまとめる。横断ルール整備、読取専用レビュー、またはプロジェクト規則で不要とされた作業では作成しない。

```text
docs/task-records/
  _category_.json
  <進行中タスクスラッグ>/       # 進行中は task-records 直下
    _category_.json
    index.md
    task-definition.md       # sidebar_position 1
    requirements.md          # 2
    basic-design.md          # 3
    detailed-design.md       # 4
    verification-matrix.md   # 5
  completed/                 # 完了済み層（label: 完了済み）
    _category_.json
    <完了タスクスラッグ>/       # フェーズ 8 で draft を外すのと同時にここへ移動
      ...（上と同じ構成）
```

進行中のタスクᴳ記録は `task-records/` 直下に置き、完了時に `completed/`（Docusaurus の label「完了済み」）配下へ移動して一覧の見通しを保つ。

- 各mdは Front Matter（`title` / `sidebar_position`）を付ける。作業中は `draft: true` とし、フェーズᴳ 8で確定時に外す。**`draft` を外すのと同一のタイミング（フェーズᴳ 8）で、当該タスクᴳのフォルダを `task-records/completed/`（完了済み層）へ移動する**
- task-recordsᴳは完了後に書き換えない時点スナップショット。現行の正ᴳは `specs/`・`design/`、決定履歴は `adr/` に置く（CR-064）
- フェーズᴳ 0の合意内容は会話内で先に成立させ、フェーズᴳ 1でタスクスラッグᴳを確定してから `task-definition.md` へ保存する

## 進行中の成果物変更（仕様変更時の遡及修正）

CR-075 が参照する手順。合意済みのフェーズᴳ成果物と、後から決まった内容が矛盾した場合に適用する。

- 適用: フェーズᴳ 0〜7 の進行中に、合意済みのフェーズᴳ成果物と矛盾する決定があった場合
- ステップᴳ:
  1. 矛盾する成果物を上流方向へ辿って特定する（タスクᴳ定義 / 要件 / 基本設計 / 詳細設計 / 検証対応表のうち、影響するものに限定する）
  2. 矛盾箇所だけを修正する。合意時点の記述を全面的に書き直さない
  3. 修正箇所に変更日と根拠（依頼者指示・独立監査指摘・実機検証結果等）を併記する
  4. 受入条件ᴳ・TC-IDᴳ へ影響する場合は検証対応表まで同期し、テストの追加・変更の要否を判断する
- アウトプット: 矛盾を解消した各フェーズᴳ成果物
- 完了条件: 修正後の成果物へ依頼者が合意する
- 先送りの禁止: フェーズᴳ 8 へ持ち越さない。矛盾を残したまま実装・テストへ進むと、品質ゲートの独立監査まで検出できない
- 確定後の扱い: フェーズᴳ 8 で `draft` を外した後の task-recordsᴳ は変更不可とする。以降の仕様変更は新しいタスクᴳとして扱い、現行の正ᴳ（`docs/specs/`・`docs/design/`・`docs/adr/`）を更新する

## 検証の共通定義

- 定義済み自動テスト: ①AC-IDᴳに対応する自動テスト ②変更影響に基づく回帰テスト ③プロジェクトまたはCIが標準指定するテスト
- リポジトリ全体の標準テストより狭い範囲だけを実行する場合は、対象範囲・除外範囲・理由を検証対応表へ記録する
- 手動検証は、自動化が不可能または著しく不合理な受入条件ᴳだけに用いる。理由、再現可能な手順、期待結果、実施結果、証跡の所在を記録する
- 手動検証は CR-025 が要求するコードテストの代替にしない
- lintが未導入なら設定・標準コマンドが存在しない根拠を添えて `非該当`、手動対象がなければ `対象なし` と記録する。実施対象があるのに環境制約で実行できない場合だけ検証待ちキューᴳへ記録する
- 全TC-IDᴳを1つ以上のAC-IDᴳまたは直接検証へ対応付け、最終状態と証跡を下記の正規の消込先へ記録する

### TC-IDᴳの最終消込先

| 作業形態                                    | 消込先                   |
| ------------------------------------------- | ------------------------ |
| task-recordsᴳを作成する                     | `verification-matrix.md` |
| プロジェクト作業でtask-recordsᴳを作成しない | `worklog.md`             |
| CR-068 対象の横断作業                       | 最終報告                 |

どの消込先でも `TC-IDᴳ / 対応AC-IDᴳまたは直接検証 / 最終状態 / 証跡` を記録し、全行が合格になるまでタスクᴳを完了しない。反映後にしか取得できない証跡は「反映後のremote証跡を要する経路」に従い、事前指定した外部記録先で最終消込を行う。

## フェーズᴳ 0: タスクᴳ定義

- インプット: 依頼者の指示 / 開始手続きᴳで把握した状態
- ステップᴳ:
  1. 理解した依頼を復唱し、認識差を解消する
  2. 主種別を1つ、副種別を0個以上選ぶ
  3. ゴール・スコープ・スコープ外・制約を明確化する
  4. タスクᴳの完了条件へTC-IDᴳ（TC-NN）を振り、検証方法または必要な証跡を定める
  5. 適用経路、非該当フェーズᴳと理由、DoDᴳを適用表から選ぶ
  6. repository内変更がある場合はGit実行モードを`human`／`ai-pr`から選ぶ（標準は`ai-pr`）。repository、base／作業branch、remote、PR base、タスクscope、worktree使用と担当を固定する
  7. merge・必須CI・配備・実機確認のうち今回の完了条件に含む範囲と、反映後結果・終了記録の対象リポジトリ外の保存先を定める。CR-068対象は最終報告とする
- アウトプット: 会話内で合意されたタスクᴳ定義。リポジトリ内開発ではフェーズᴳ 1で `task-definition.md` へ保存する
- 完了条件: 依頼者がタスクᴳ定義に合意し、repository内変更ではGit実行モードと対象scopeが一意である

## フェーズᴳ 1: タスクᴳ記録初期化・必要時の名称提案

- インプット: 合意済みタスクᴳ定義
- ステップᴳ:
  1. ブランチを使う場合はブランチ名候補を提示する（CR-060）
  2. チャット名を管理する場合は候補を提示する（CR-060。設定は依頼者操作）
  3. ブランチ名の記述部またはタスクᴳ名からタスクスラッグᴳを定める
  4. `ai-pr`では合意済みbase refから作業branchと必要なworktreeを作成し、worktree path・branch・remote・担当を記録する。同じbranchは他worktree／agentへ割り当てない
  5. `human`ではAIがexact commandを提示し、状態変更Git実行後にread-onlyで照合する
  6. リポジトリ内開発では選択したcheckout／worktreeに `docs/task-records/<タスクスラッグ>/` を作成し、フェーズᴳ 0の合意内容を `task-definition.md` へ保存する
- アウトプット: 必要時の確定ブランチ名・チャット名 / タスクスラッグᴳ / 必要時のtask-recordsᴳ初期一式
- 完了条件: 使用する名称について依頼者と合意し、必要な記録先へ合意済みタスクᴳ定義が保存されている。`ai-pr`はbranch／worktreeの一意な割当てを照合済みとし、記録・名称が不要な場合は理由を記録する

## フェーズᴳ 2: 要件定義

- インプット: 合意済みタスクᴳ定義
- ステップᴳ:
  1. 目的・背景・意図: なぜ行うか / 誰のためか / 成功と見なす状態を言語化する
  2. AS-IS分析: 現状の構造・データ・運用・課題・制約を整理し、断定前に実物を確認する（CR-069）
  3. TO-BE設計: あるべき姿とAS-ISとの差分を定義する。高リスク判断は関連する判断レンズᴳを併用する
  4. 機能要件 / 非機能要件 / スコープ外 / 受入条件ᴳを列挙する。active／completedのtask-recordsᴳ区分を採用し、後続consumerがtask-recordsᴳを参照する場合は、active-only／completed-onlyのexactly-one contract、both／neitherの拒否、移動後のconsumer参照を要件化する
  5. 各AC-IDᴳを上位のTC-IDᴳへ対応付け、全TC-IDᴳを1つ以上のAC-IDᴳまたは直接検証へ割り当て、自動／手動の検証方式を仮決定する
  6. reviewerᴳで要件漏れ・受入条件ᴳの客観性・根拠を独立監査する
- アウトプット: 要件定義メモ（`requirements.md`）
- 完了条件: 依頼者が要件に合意し、全TC-IDᴳの検証先が定まり、reviewerᴳの指摘が解消済みまたは依頼者裁定済みである。重要な事実主張へ根拠を併記し、未検証事項は検証待ちキューᴳへ記録する
- 補足: 受入条件ᴳは AC-IDᴳ / 上位TC-IDᴳ / Given-When / Then / 観点 / 検証方式で記述し、曖昧語を数値・境界へ置き換える

## フェーズᴳ 3: 基本設計（外部設計 / What）

- インプット: 合意済み要件定義メモ
- ステップᴳ:
  1. 方式・システム構成をトレードオフ比較し、採用理由とWhy notを残す
  2. 機能構成を設計する
  3. 外部インターフェース（画面・API・帳票等）を設計する
  4. 論理データモデルを設計する
  5. 非機能要件への対応方針を設計する
  6. フェーズᴳ 3が今回の最終設計成果物になる場合は、reviewerᴳで要件整合・方式妥当性・非機能要件を独立監査する
- アウトプット: 基本設計書（`basic-design.md`）
- 完了条件: 依頼者が基本設計に合意し、各要件に対応先があり、重要な事実主張へ根拠が併記されている。最終設計成果物になる場合はreviewerᴳの指摘が解消済みまたは依頼者裁定済みであり、未検証事項は検証待ちキューᴳへ記録する

## フェーズᴳ 4: 詳細設計（内部設計 / How）

- インプット: 合意済み基本設計書
- ステップᴳ:
  1. モジュール・クラス・関数を分割する
  2. 内部ロジックを設計する
  3. 物理データを設計する
  4. エラーハンドリングを設計する
  5. 実コードを確認して変更対象一覧を特定する（CR-069）
  6. 設計書を具体化した後、主要な入口・引数と戻り値・データ型・依存の受け渡し・呼出し関係を示すスケルトンコードを作成する。新規モジュールやインターフェース・責務・依存関係の変更を対象とし、配置先と対象範囲を設計書へ記録する。既存構造を変えない小さな修正などでは省略理由を記録する
  7. スケルトンで判明した問題を設計書とコードの両方へ反映し、未決事項と検証待ちを整理する。スケルトンは設計確認に必要な最小限とし、業務ロジックの実装はフェーズᴳ 6で行う。内部の細かな分割は後続のテスト・実装で調整でき、合意内容と矛盾する変更は前提変更時の手続きに従う
  8. reviewerᴳで設計書とスケルトン（省略時はその理由）を一緒に独立監査し、相互の整合、要件・基本設計との整合、影響範囲、非機能要件を確認する
- アウトプット: 詳細設計書（`detailed-design.md`）と必要なスケルトンコード
- 完了条件: 依頼者が詳細設計書とスケルトン（省略時はその理由）に合意し、reviewerᴳの指摘が解消済みまたは依頼者裁定済みである。変更対象の実在確認と重要な事実主張の根拠が記録されている

## フェーズᴳ 5: テスト実装（TDD・Red）

- インプット: 要件定義メモ（受入条件ᴳ・AC-IDᴳ）/ 詳細設計書 / スケルトンコード（作成した場合）
- ステップᴳ:
  1. 全AC-IDᴳを自動テストまたは手動検証へ割り当て、全TC-IDᴳの対応先を含む検証対応表を作る
  2. 自動テスト対象では合意済みの入口・契約に対して失敗するテストを実装し、期待どおり失敗すること（Red）を確認する。スケルトンを作成済みなら引き継ぎ、テスト実行に必要な最小限の骨組みを補う。スケルトンの作成や構文確認だけでRed確認済みとはしない
  3. 手動検証対象では自動化しない理由、再現手順、期待結果、証跡の保存先を定義する。Redは非該当と記録する
  4. 定義済み自動テストの範囲と、標準テストから除外する範囲・理由を記録する。active／completedのtask-recordsᴳ lifecycleを要件化した場合は、active-only／completed-onlyの正常系、both／neitherの異常系、反対側を読まないこと、移動後のconsumer回帰を検証へ割り当てる
- アウトプット: テストコード / 検証対応表（`verification-matrix.md`）
- 完了条件: 受入条件カバレッジᴳが100%で、自動テスト対象は期待どおりRed、手動検証対象は再現可能な手順と期待結果が定義済みであり、依頼者がテスト・検証設計に合意する

## フェーズᴳ 6: 実装（TDD・Green）

- インプット: Red確認済みテストコード / 詳細設計書 / 検証対応表
- ステップᴳ:
  1. CR-070の明示が未実施、または対象・方針が変わった場合は、編集前に変更対象と変更方針を明示する
  2. テストを通す最小実装を書く（Green）
  3. 新規依存は理由を提示し、承認後に追加する（CR-027）
- アウトプット: 実装コード
- 完了条件: 定義済み自動テストがグリーンで、構文確認と利用可能なlintを通し、依頼者が実装成果物に合意する。実施対象があるのに実行不能な項目は検証待ちキューᴳへ記録する

## フェーズᴳ 7: リファクタ（TDD・Refactor）

- インプット: 実装コード / テストコード / 検証対応表
- ステップᴳ:
  1. 依頼範囲内の改善点を重大度と対応要否付きで整理する
  2. リネーム時は使用箇所を確認し、すべて対応する
  3. 定義済み自動テストと定義した手動検証を実施し、挙動不変と受入条件ᴳ充足を確認する
  4. reviewerᴳで最終diff・テスト結果・受入条件ᴳの充足・回帰リスクを独立監査する
  5. 検証対応表へ全TC-IDᴳの最終状態・証跡・監査指摘の対応状況を記録する
- アウトプット: リファクタ済みコード / 最終化した検証対応表
- 完了条件: 定義済み自動テストと定義した手動検証が完了し、reviewerᴳの必須指摘が解消済みまたは依頼者裁定済みで、依頼者がリファクタ後成果物に合意する。反映後にしか確認できない項目に限り、上記専用経路の待ち状態と手順・外部記録先を明記し、反映前に可能な検証と安全性確認が済んだ成果物を次工程へ渡す

## フェーズᴳ 8: ドキュメント整備・完了記録

- インプット: 適用経路で作成した全成果物
- ステップᴳ:
  1. 仕様・設計変更は `docs/specs/`・`docs/design/` 等の現行の正ᴳへ反映する
  2. 重要な決定があれば `docs/adr/` へADRを追加する
  3. リポジトリ内開発ではtask-recordsᴳの `draft` を外し、時点スナップショットとして確定する。active／completed区分を採用する場合はcompletedへ移した後にcompleted-only回帰を実行し、active側の不存在とconsumer参照の到達を確認する
  4. プロジェクト作業では `worklog.md` と `resume.md` を更新し、節目に該当する場合だけhandoverᴳを作成する
  5. 横断作業では最終報告へ実施内容・DoDᴳ・未検証事項を記録する
  6. 本書の「TC-IDᴳの最終消込先」に従い、全TC-IDᴳの最終状態と証跡を消し込む
  7. 変更範囲へ `03_Checks` を実行し、違反を修正または報告する
  8. 完了配置への移動・参照修正を含むリポジトリ内文書をPR前に揃える。反映前成果物の確定とmerge・配備成功を区別し、未実施の結果を先書きしない
- アウトプット: 更新済みの正ᴳ / 確定したtask-recordsᴳ / 必要な継続記録または最終報告
- 完了条件: 全TC-IDᴳがAC-IDᴳまたは直接検証へ対応して合格し、適用表のDoDᴳをすべて消し込み、必須検証の残件がなく、文字・参照・正ᴳの整合を満たした成果物に依頼者が合意する。反映後にしか確認できない項目に限り、上記専用経路の待ち状態・検証手順・外部記録先を確定して進める（タスクᴳ完了ではない）。

## フェーズᴳ 9: 振り返り

- インプット: 当該タスクᴳで発生した失敗・指摘・独立監査の結果 / 当該タスクᴳ区間の `worklog.md` エントリ全件 / 適用経路で作成した全成果物 / 既存の失敗記録台帳
- ステップᴳ:
  1. 当該タスクᴳの失敗・指摘・手戻りを列挙する。依頼者からの指摘、独立監査の必須指摘、自分で気づいた誤りを区別せずすべて対象にする
  2. 各件を「事象 → 原因 → 仕組み化」の3点で分析する（CR-002）
  3. CR-014〜CR-018 に従い失敗記録台帳へ記録する。1回目は `様子見`、ルール化済みの再発は `再発` とする
  4. CR-001 の追記トリガーに該当する件について、ルール追記・改訂の候補を配置判定（CR-004 / CL-008 / PJ-003）付きで提示する
  5. 有効だった手順・回避策も記録対象に含める（失敗だけを対象にしない）
  6. 裁定に伴う承認済み変更、一時資料の後始末、参照修正を済ませ、必要な再検証を行う。既存資料の保護指示を優先し、削除は権限内の対象だけに限る
  7. 終了手続きのチェックリストを前倒しで照合し、リポジトリ内で必要な変更が残っていないことを確認する。確定済みtask-recordsᴳの仕様変更が必要なら確定後の規則に従い、黙って書き換えない
- アウトプット: 失敗記録台帳の追記エントリ / ルール追記・改訂の候補一覧
- 完了条件: この時点までの当該タスクᴳの失敗・指摘がすべて台帳へ記録され、ルール追記候補へ依頼者が裁定を示し、承認済みのリポジトリ内変更・必要な再検証・変更漏れ確認が済んでいる。指摘等が0件の場合も変更漏れ確認を行い、「該当なし」と明示する
- 補足: タスクᴳ途中のセッション分割だけを理由に本フェーズᴳを実施しない。途中の気づきは `worklog.md` の「決定と理由」欄（CR-055）が受け止め、PR前に当該時点までの区間全体を振り返る。後からCI・review・実機確認で新たな指摘が生じた場合は、外部台帳へ追記・裁定し、修正が必要なら該当工程へ戻す

## フェーズᴳ 10: コミット・push・PR引渡し

- インプット: フェーズᴳ 9 までの全成果物 / `git status` と `git diff` の実測結果
- ステップᴳ:
  1. `git status` / `git diff --stat` で変更・未追跡ファイル全体を把握する（CR-061 の読み取り専用操作）
  2. 下記の粒度基準に従いコミット単位へ分解し、依存順に並べる
  3. 各コミットについて 対象ファイル / 要約行 / 本文（Why。CR-023）/ `[ai]` 付与の要否（CR-028）を含むコミット計画を提示する
  4. 中間コミットでテストが通らない単位がある場合は、どのコミットから緑になるかと `git bisect` が効かない区間を計画へ明記する
  5. コミット対象から外すファイルがある場合は、対象と理由を明示する
     原則としてフェーズᴳ 9までの全成果物を1つのPRへ集約する。意味単位の複数commitは許容するが、文書整備・終了記録だけを予定された後続PRへ残さない。CI・review起因の修正は同一PRへの追加commit・pushとし、合意済みの先行反映が必要な場合は理由を記録する
  6. `ai-pr`では各単位のexact paths／hunksだけをstageし、`git diff --cached`で混入なしを確認する。作業tree全体Greenとcommit単独Greenを区別し、単独tree未検証はcandidate Greenと記録する
  7. `ai-pr`では計画順にcommit・push・PR作成または同一PRへの通常の追加commitを行う。`human`ではexact commandと対象を引き渡し、依頼者が実行または保留を判断する
  8. commit／push／PR後はcommit hash、remote branch、PR URL、CI／check、残り差分、staged状態をread-onlyで照合する。想定外混入時はamend／resetせず停止する
- アウトプット: コミット計画 / `ai-pr`のcommit・remote branch・PR・事後照合、または`human`のexact引渡しと実行／保留判断
- 完了条件: `ai-pr`は計画したcommit・push・PR作成と事後照合が完了し、最終review／mergeを人間に引き渡している。`human`は計画とexact commandを提示し、依頼者が実行または保留を判断している
- 適用条件: リポジトリ内の変更がある場合のみ適用する。CR-068 対象の横断作業でも、対象がGit管理下なら本フェーズᴳを適用し、記録先は CR-068 に従う。リポジトリ内変更がない場合は非該当とし、その理由をタスクᴳ定義へ記録する
- 本フェーズᴳのPR引渡し完了とタスクᴳ完了を区別する。人間merge・必須CI・今回の完了条件に含む反映後確認が揃った後に終了手続きᴳへ進む。`human`で実行保留の場合も残件を記録し、反映完了とは扱わない。リポジトリ内変更のないタスクᴳはフェーズᴳ 9と必須確認の完了後に終了手続きᴳへ進む

### コミット粒度

上から順に適用する。

| 層            | 基準                                                                                                                                          | 根拠                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1. 意味単位   | 1コミット = 1つの完結した変更意図。要約行が「〜と〜」「〜し、〜」で並列にならずに書けることを判定基準とする                                   | 並列で書けてしまう時点で2つの意図が混ざっている                                    |
| 2. 依存順     | 新規モジュール（葉）を先に、それを使うハブを後に積む                                                                                          | 逆順だと中間コミットで未解決の参照が生じる                                         |
| 3. 種別の分離 | 次を同一コミットに混ぜない: ①挙動変更 と 純粋リファクタ（移動・改名） ②新規モジュールの追加 と 既存への配線 ③機械的な一括変換 と 手書きの変更 | レビュー時に diff の読み方が変わり、「移動か改変か」の判別に読み手のコストがかかる |

- 同一コミットにまとめてよいもの: コードと、そのコードが正ᴳとなる設計資料の更新（分けると設計と実装が食い違う中間状態が履歴に残る）/ 実装と対応するテスト
- 独立させてよいもの: 誤字・リンク修正など、意味を変えないドキュメント単独の変更
- 層1を満たせない場合: ハブに変更が集中している等の理由で分解できないことがある。**分解できない理由を計画へ明記**したうえで許容する

### 実行主体について

Git実行主体はPhase 0で選んだ`human`／`ai-pr`とプロジェクト規則に従う。`ai-pr`はAIが標準Git lifecycleを実行し、PRの最終review／mergeと履歴破壊操作は人間が担う。`human`はAIが計画・exact command・read-only事後照合を担い、状態変更Gitを人間が実行する。どちらでもCR-023（Why）とCR-028（`[ai]`）を維持する。
