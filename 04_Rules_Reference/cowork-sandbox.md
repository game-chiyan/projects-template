- 参照元: `04_Rules_Reference\README.md` の参照トリガー
- 更新: 追記・変更・削除はすべて提案 → 依頼者承認後に反映する。採番は `CROSS_PROJECT_RULES.md` の ID採番ルールに従う

## ルール

- CS-001: マウント先での削除系（`os.remove` / `os.rmdir` / `rm`）は使わず、移動・置換は「内容書換 → `os.rename`（上書きリネーム可）」で行う（2026-07-11: docs 配置換えで削除系のみ EPERM、rename は成功）
- CS-002: ホスト側ツールで書いた直後のファイルがサンドボックス側の読取で途切れて見えることがある。実破損と判断する前にホスト側 Read で実ファイルを確認する（2026-07-11: 書込直後の index.md が 100 バイトに見えたが実ファイルは正常）
- CS-003: ホスト側 Edit が「modified since read」エラーになったら、対象ファイルを Read で再読込してから再実行する（フォルダ接続直後に頻発。2026-07-11: 3回観測、いずれも再読込で解消）
- CS-004: ホスト側ツールの編集でファイルが伸びた直後は、サンドボックス読取が旧サイズで末尾欠落することがある。当該ファイルのサンドボックス検証は行わず、依頼者ローカルでの実行・確認を正ᴳとする。サンドボックス側で内容が必要な場合は新規パスへ書き出して使う（2026-07-14: 同一セッションで4ファイルに発生）
- CS-005: サンドボックスで実行する危険文字スキャンは、対象文字をリテラルではなくエスケープ表記（`\uXXXX`）で記述する。heredoc 転送時に不可視文字リテラルが別の文字へ化け、スキャン自体が誤検出・見逃しを起こすため（2026-07-17: NBSPリテラルが半角スペースへ化け、全行を誤検出する偽陽性5273件が発生）。エスケープ表記でも `bash -c '...python3 - <<EOF...'` 経由だと化ける事例が再々発したため、確実を期すならスキャンスクリプトを `.py` ファイルに `Write` で書き出してから `python3 <path>` で実行する（2026-07-17: heredocでNBSPリテラル化けが3回再発、ファイル化実行で解消。スクリプトは scratchpad の `outputs/` 等へ書き出す）。プロジェクトに専用の検査（`npm run check:unicode` 等）がある場合はアドホックなスキャンを書かずにそれを使い、対象外の文字を調べるときだけスクリプトをファイルへ書き出して実行する
- CS-006: マウント型Cowork sandboxからマウント先repositoryの `git` を実行するときは、`--no-optional-locks`を付け、作業tree・index・refs・remoteを変えないsubcommandに限定する。所有者不一致は対象pathだけをcommand-local `safe.directory`に指定し、state-changing Gitは合意済みGitモードに従って安全なlocal host／Codex worktreeへroutingする。これはマウント越しの `.git/index.lock` 残留を防ぐ技術保護であり、local workspaceの`ai-pr`を禁止しない（2026-07-20 の事象が 2026-07-22・2026-07-25 に再発。2026-07-31 にread-only操作へ緩和、2026-09-01 にlocal実行へのroutingを明確化）
- CS-007: マウント先の `node_modules` はホスト（Windows）向けに導入されているため、`.bin` の shim はサンドボックスで実行できない（`exec: node.exe: not found`）。`node node_modules\<パッケージ>\bin\<エントリ>` を直接起動すればフォーマッタ・リンタ等をサンドボックスから実行できる（2026-07-26: prettier・eslint で確認）
- CS-008: テストランナー本体をサンドボックスで実行できない場合は、まず CS-009 を試し、それが不可能な場合に本ルールへ退避する。本ルールでは、テストコードを写した確認用スクリプトを別に書かず、**ランナーの import だけを最小 shim へ差し替えてテストファイルの実物を `node` で読み込む**。`node:module` の `register` で解決フックを登録し、対象 specifier（例: `vitest`）を shim の URL へ写す。shim はテストが実際に使う API だけ実装する。ハーネスはリポジトリ外へ置き、リポジトリへ持ち込まない。**shim が実装できない API を使うスイートは実行できないため、実行対象の解決自己検査（対象が関数として解決できることの確認）を同梱し、未実行を合格と数えない**（CR-084）。合否の正ᴳ は依頼者ローカルのランナー実行とする（CR-062）。2026-08-02: vitest 実行不可の環境で `main.test.js` の実物を走らせ、得た NG 14 件が依頼者ローカルの `npm run verify` の 14 件とラベル・期待値・実際値まで一致した
- CS-009: サンドボックスでテストランナー・ビルド検査を実行する必要があり、マウント先の `node_modules` がホスト向けで動かない場合は、**リポジトリ外**（`/tmp` 等）へ `package.json` と `package-lock.json` を写して `npm ci` し、実ソースのディレクトリへ symlink を張って実行する。マウント先の `node_modules` と lock は変更しない（ホスト側の実行環境を壊さないため）。合否の正ᴳ は依頼者ローカルの実行結果とし（CR-062）、サンドボックス実行は実装中の自己確認に限る。レジストリへ到達できない、または Linux ビルドが無い依存がある場合は CS-008 の shim 方式へ退避する。サンドボックスはセッションごとに初期化されるため、毎セッション再実行が必要（2026-08-06: `workerd` と `rolldown` の Windows バイナリにより、テストランナーと bundle bytes 検査がいずれも実行不可だった）。ただし bundle サイズを計測する検査では symlink を使わない。esbuild は symlink を実パスへ解決するため、バンドルへ埋まるパス文字列が伸びて bytes が変わる（2026-08-06: parent が 197417 に対し symlink 経由で 201411 と +3994 bytes ずれ、誤った超過判定を出した）。計測時はソースをコピーし、既知の基準値と一致することを確認してから土台として使う（CR-084）
